## 一、实验目的

1. 设计并实现一个基于**流式 Socket（TCP）**的聊天协议，聊天消息须携带时间信息；
2. 用 C/C++ 基于**基本 Socket 函数**实现服务器与客户端，不使用封装后的 Socket 类或框架；
3. 支持**多线程**与**多人聊天**，程序结构清晰、可读性好；
4. 支持**中英文**混合聊天；
5. 设计并**实测数据包丢失**的检测与统计机制；
6. 完成实验报告与源码整理。

## 二、协议设计

完整协议规范见 [`docs/协议设计.md`](协议设计.md)，此处给出要点。

### 2.1 报文结构

TCP 是字节流，无消息边界，因此协议必须自带切帧依据。采用**「ASCII 头部行 + 定长主体」**结构：

```
┌──────────────────────────────────────────────┐
│ ① 头部行 (ASCII, 以 '\n' 结束)                │
│    CHT1 <TYPE> <SEQ> <TS> <SENDER_LEN> <PAYLOAD_LEN>\n
├──────────────────────────────────────────────┤
│ ② SENDER  (SENDER_LEN 字节, UTF-8)            │
├──────────────────────────────────────────────┤
│ ③ PAYLOAD (PAYLOAD_LEN 字节, UTF-8)           │
├──────────────────────────────────────────────┤
│ ④ CRC32    (4 字节, 大端序)                   │
└──────────────────────────────────────────────┘
```

- 头部用 ASCII 是为了**可读性**：抓包后可直接肉眼核对，测试时也便于手工构造报文；
- 长度字段以**字节数**给出，因此中文（UTF-8 每字 3 字节）与英文在协议层完全等价，无需任何转义；
- 主体总长 `= SENDER_LEN + PAYLOAD_LEN + 4`，接收方据此从字节流中精确切帧；
- 负载与头部物理分离，故负载可含 `\n`、空格等任意字符。

### 2.2 报文类型与语义

| TYPE | 名称 | 方向 | 语义 |
|------|------|------|------|
| 1 | `LOGIN_REQ` | C→S | 登录请求，必须是连接首帧，负载为昵称 |
| 2 | `LOGIN_ACK` | S→C | 登录确认，同时告知分配的用户编号与用户名 |
| 3 | `LOGOUT` | C→S | 主动下线 |
| 4 | `CHAT` | 双向 | 群聊消息，服务端广播给全部在线用户 |
| 5 | `SYSTEM` | S→C | 系统通知（加入/离开/错误提示） |
| 6 | `USERLIST` | S→C | 在线用户列表，`\|` 分隔 |
| 7 | `PING` | 双向 | 心跳探测，载荷为时间戳；载荷为 `"who"` 时表示请求在线用户列表 |
| 8 | `PONG` | 双向 | 心跳应答，回显 PING 载荷 |
| 9 | `ACK` | S→C | 应用层确认，载荷为被确认帧的序号 |
| 10 | `LOSS_REPORT` | S→C | 告知客户端丢失了多少报文 |
| 11 | `NICK_CHANGE` | C→S | 请求修改昵称，载荷为新昵称 |
| 12 | `NICK_ACK` | S→C | 改名结果，载荷为生效的新昵称 |

### 2.3 时间信息的设计

协议头部含 `TS` 字段（Unix 毫秒时间戳）。关键约定是：

> **服务端转发 `CHAT` 时原样保留客户端填入的 `TS`**，而非改成转发时刻。

因此群聊中所有成员看到的同一条消息**时间戳完全一致**，符合"聊天信息带时间"的语义，
且时间为**消息产生时刻**而非**网络传输时刻**，语义更准确。

### 2.4 序号与丢包检测语义

- `SEQ` 作用域为**一条连接**，由发送方维护，从 1 逐条 +1；
- 发送方保证「分配序号 + 写帧」原子化（同一互斥锁），故接收方看到的序号单调递增；
- 接收方判据：`recv_seq > last_seq_in + 1` ⇒ 丢失 `recv_seq - last_seq_in - 1` 帧。

## 三、模块划分与流程

完整说明与全部流程图见 [`docs/模块设计.md`](模块设计.md)。

### 3.1 模块清单

| 模块 | 文件 | 职责 |
|------|------|------|
| 协议模块 | `protocol.h/.cpp` | 帧编解码、CRC32 校验、时间戳格式化 |
| 网络 I/O 模块 | `net_io.h/.cpp` | 流式切帧、阻塞 socket 收发、写锁保护 |
| 会话管理模块 | `server.cpp` | 在线用户表、登录/登出、编号分配 |
| 转发模块 | `server.cpp` | 群聊广播、系统通知、用户列表同步 |
| 连接线程模块 | `server.cpp` | 每连接一线程，循环收帧与分发 |
| 可靠性模块 | 双端 | 序号缺口检测、丢包统计、人工丢包注入 |
| 心跳模块 | `server.cpp` | 定时 PING，超时回收失联连接 |
| 命令模块 | `client.cpp` | `/nick` `/who` `/ping` `/test` `/stat` `/quit` |

### 3.2 服务器主流程

```
main() → platform_init() → create_listen_socket() → 启动心跳线程
      → accept() 循环 → 创建 Client → 加入用户表 → thread_start(连接线程)
```

### 3.3 连接线程流程

```
conn_read_frame() → r==0(对端关闭) / r<0(协议错) / r==1(正常)
                  → check_seq() 序号连续性检测
                  → 按 TYPE 分发 (LOGIN_REQ / CHAT / PING / LOGOUT ...)
                  → 收尾: 从用户表移除 → 广播下线通知 → 关闭连接
```

### 3.4 并发设计

| 并发点 | 保护措施 |
|--------|----------|
| 多线程写同一连接 | 每连接 `send_mu`，且"分配序号+写帧"在同一临界区 |
| 读写在线用户表 | 全局 `g_clients_mu`；采用"加锁拷贝快照→锁外遍历" |
| 心跳线程与连接线程共享 `Client` | 用 `shared_ptr<Client>` 持有，杜绝悬垂指针 |
| 客户端收发并行 | 接收线程 + 主线程分离 |

## 四、程序实现

### 4.1 使用基本 Socket 函数

全项目仅使用原生 Socket API，**未使用任何 Socket 封装类库**：

```c
socket()  bind()  listen()  accept()  connect()
send()    recv()  setsockopt()  shutdown()  closesocket()
```

`socket_compat.h` 仅做 **Winsock2 的初始化与少量接口适配**
（`WSAStartup` / `WSACleanup` / `closesocket` / `SOCKET` 强转 / 睡眠与控制台代码页），
不提供任何面向对象的封装接口；
`net_io.h` 中的 `Conn` 只是一个**数据聚合体**（fd + 互斥锁 + 接收缓冲区），函数仍是全局 C 风格函数。

### 4.2 关键实现：流式切帧

TCP 无消息边界，一次 `recv` 可能返回半条报文或数条报文。`net_io.cpp::conn_read_frame()` 的处理：

```c
/* 1. 先切出完整头部行 (直到第一个 '\n') */
for (;;) {
    if (take_line(c.rbuf, header)) break;      /* 凑齐一行 */
    if (c.rbuf.size() > MAX_HEADER_LEN) { 协议错误 }
    n = raw_recv(c.fd, tmp, sizeof(tmp));       /* 继续读字节流 */
    c.rbuf.append(tmp, n);                      /* 存入接收缓冲区 */
}
/* 2. 解析头部得到主体长度 */
parse_header_line(header, msg, slen, plen, err);
body_len = slen + plen + 4;
/* 3. 读满恰好 body_len 字节 */
while (c.rbuf.size() < body_len) { ... }
/* 4. 切分主体并校验 CRC32 */
```

### 4.3 关键实现：写帧原子化

TCP 的 `send` 不保证一次发完，且多线程并发写同一 socket 会导致**帧交叉错乱**。
因此 `conn_write_frame()` 在**写锁内**完成"编码 + `send_all()` 全量发送"：

```c
std::lock_guard<std::mutex> lock(c.send_mu);
return send_all(c.fd, frame.data(), frame.size());   /* 内部循环处理短写 */
```

服务端 `send_frame()` 更进一步，把**序号分配**也放进同一临界区，
保证「序号 N 的帧」一定先于「序号 N+1 的帧」写出。

### 4.4 中英文支持

- 协议层：全部文本字段 UTF-8，长度按**字节数**计算，中英文同等对待；
- Windows 控制台：启动时调用 `SetConsoleOutputCP(CP_UTF8)` 与 `SetConsoleCP(CP_UTF8)`，
  保证中文在控制台正确显示与输入；
- **命令行参数**：Windows 的 `argv` 是系统 ANSI 代码页（中文系统为 GBK）的字节，
  程序按 UTF-8 处理会乱码，因此改用 `GetCommandLineW()` + `CommandLineToArgvW()`
  取未经 ANSI 转换的 Unicode 参数，再逐个转成 UTF-8；
- 程序名同样取自 `GetCommandLineW()` 的**宽字符**命令行再转 UTF-8，
  避免 `argv[0]` 在中文 Windows 上是 GBK 字节而导致路径乱码。

### 4.5 多线程与多人聊天

- 服务器：主线程 `accept`，**每个连接启动一个独立线程**处理，天然支持任意多客户端；
- 客户端：**接收线程 + 主线程**双线程结构，主线程读 `stdin`，接收线程读 socket，二者互不阻塞；
- 群聊采用广播实现，`MSG_USERLIST` 实时同步在线成员。

### 4.6 用户编号与用户名

- 服务端为每个连接分配一个**单调递增的用户编号** `id`（从 1 开始）；
- 客户端**未指定昵称**（未传 `-n`）时，登录帧载荷为空，服务端按连接顺序分配默认用户名
  `pc1` / `pc2` / `pc3` …；用 `-n 张三` 指定则以指定的为准；
- 登录应答 `LOGIN_ACK` 的载荷格式固定为
  `登录成功, 你的用户编号是 <id>, 用户名是 <nick>`，
  **编号与用户名一并给出**，客户端据此回填自己的昵称并用于后续发言署名；
- 客户端的昵称会被主线程（`/nick` 改名）与接收线程（回填服务器分配的昵称）同时读写，
  因此用 `g_nick_mu` 保护，并通过 `nick_get()` / `nick_set()` 访问，杜绝数据竞争。
- **改名与登录是两种不同的语义**，用两种不同的报文表达：
  改名走 `NICK_CHANGE`（C→S），服务端处理后
  ① 在服务器日志留下一条独立记录 `用户 旧名(id=N) 将昵称改为 新名`；
  ② 用 `NICK_ACK` 把生效的昵称回复给改名者本人（不回填本地昵称，直到收到确认，
     保证服务端拒绝非法昵称时两端状态仍一致）；
  ③ 向**其他**在线用户广播 `NICK_CHANGE` 语义的系统通知 `用户 旧名(id=N) 将昵称改为 新名`；
  ④ 全量广播更新后的在线用户列表。
  改名**不会**产生"加入了聊天室"这类加入/离开通知——详见 §6 第 18 条。

### 4.7 时延（RTT）测量

- `PING` 帧的载荷是发送时刻的 **Unix 微秒时间戳**，`PONG` 原样回显，
  接收方用 `now_us() - 载荷` 得到往返时延；
- 计时器使用 `QueryPerformanceCounter`（硬件高精度计时器），
  与启动瞬间的 FILETIME 墙上时钟**双时钟对齐**，兼顾 Unix 时间语义与亚毫秒分辨率；
- **为什么不用 `GetSystemTimeAsFileTime`**：其实际刷新粒度是系统时钟节拍（典型 15.6 ms），
  连续两次读取常常相同，差值恒为 0；
- **为什么不用毫秒**：本机回环的真实 RTT 不足 1 ms，整数毫秒会恒显示 `0`。

实测（同机回环）：

```
[2026-11-04 17:17:27.945] Pong: 往返时延 RTT = 195 us (0.195 ms)
[2026-11-04 17:17:28.268] Pong: 往返时延 RTT = 494 us (0.494 ms)
[2026-11-04 17:17:28.661] Pong: 往返时延 RTT = 493 us (0.493 ms)
```

**"所有人都在同一台电脑上，为什么还有时延？"** ——回环（loopback）是**虚拟网卡**，
数据仍要走完整的内核网络栈（AFD → TCP → IP 回环驱动 → TCP → AFD），去一趟、回一趟共两次，
再加上两次**线程唤醒**（服务端连接线程阻塞在 `recv()`，数据到达后由内核唤醒、调度器调度），
以及切帧 / CRC32 / 发包等自身开销，实测 0.2~0.5 ms 与该量级估算一致。
参考量级：同机回环 0.2~0.5 ms，局域网 1~10 ms，跨城公网 30~100 ms。

### 4.8 用户的动态增减

**增**：客户端连上 → `accept` → 分配**单调递增的用户编号** `id`（`g_next_id++`，不复用）
→ 加入全局用户表 `g_clients` → 启动**独立连接线程** → 处理 `LOGIN_REQ` →
广播"xxx 加入了聊天室" + 全量 `USERLIST`。

**减**（两条路径，都收敛到同一段收尾代码）：

| 路径 | 触发 | 收尾动作 |
|------|------|----------|
| 正常退出 | 客户端发 `LOGOUT` 后 `shutdown` | 服务端记 `主动退出`，`recv` 返回 0 → 收尾 |
| 异常掉线 | 客户端进程被 kill / 网络断 | 服务端 `recv` 报 `WSAECONNRESET` → 收尾 |

收尾时：从用户表**摘除**该连接 → 广播"xxx 离开了聊天室" → 广播新的全量 `USERLIST`。
因此**在线列表在任意时刻都保持正确**，其余在线用户立刻能看到增减结果。

**并发安全**：用户表用 `g_clients_mu` 保护；广播时先把 `shared_ptr` 列表**快照**一份
再释放锁，然后逐个发送 —— 这样"持锁时不做 I/O"，避免一个慢客户端拖住所有人；
`shared_ptr` 保证广播途中连接线程释放对象也不会造成悬垂指针。

**实测**（12 接入 → 强杀 5 个 → 再补 3 个）：

```
=== 1. 逐个接入 12 个客户端 ===
online count = 12
list = ['pc1','pc2','pc3','pc4','pc5','pc6','pc7','pc8','pc9','pc10','pc11','pc12']
is pc1..pc12 = True

=== 2. 突然 kill 5 个客户端 (模拟异常掉线, 没有 /quit) ===
online count = 7
list = ['pc1','pc2','pc3','pc4','pc5','pc11','pc12']      <- pc6..pc10 已被摘除
shrunk correctly = True

=== 3. 再补接入 3 个客户端 ===
online count = 10
list = [...,'pc13','pc14','pc15']
grew correctly = True

=== 4. 新加入者发一条消息, 统计多少个客户端收到 ===
receivers = 10 / online 10                              <- 含发送者本人
```

服务器日志同时留痕（本次修复新增，见 §6 第 17 条）：

```
[17:30:26.575] 读取报文失败: 连接被对端重置(异常断开)
[17:30:26.575] 用户 pc7(id=7) 断开连接, 已从用户表移除
```

**规模与已知边界**：

- 服务器**不设用户数上限**，每连接一线程 + 一个套接字；
  在 Windows 上受线程数与文件句柄数限制，实测十几到几十人毫无压力，
  几百人仍在同一量级（瓶颈会先出现在线程调度而非业务逻辑上）。
- **用户编号唯一且永不复用**；**昵称（用户名）不强制唯一** ——
  两个客户端都用 `-n Alice` 会得到两个 `Alice`，在线列表里就会出现重复项。
  这是有意的设计：真正的主键是**用户编号**，昵称只是显示名；
  这也正是 §4.6 要"编号与用户名一起显示"的原因 ——
  列表里只看昵称无法区分同名用户，看编号则一目了然。

### 5.3 测试一：三人并发聊天（中英文）

启动服务器后，三个客户端 Alice / Bob / Carol 同时在线，交错发送中英文消息。
自动校验脚本 `test/multi_test.py` 检查：每人是否收到他人**全部**消息、中文是否完整、序号是否连续。

**实测输出（Carol 客户端的部分记录）：**

```
[2026-11-04 13:19:02.076] Alice: Hello from Alice, this is English.
[2026-11-04 13:19:02.427] Bob: Hi, Bob here in English.
[2026-11-04 13:19:02.777] Carol: Greetings from Carol.
[2026-11-04 13:19:03.128] Alice: Alice says 中文消息 number one.
```

### 5.4 测试二：服务端 → 客户端 方向丢包检测

TCP 本身通过重传与确认保证**传输层不丢包**，因此应用层正常情况下**观察不到丢包**。
为验证丢包检测机制的有效性，服务器提供 `--drop <percent>` 参数**人工注入丢包**
（丢弃数据类报文，但**先分配序号再丢弃**，从而在序号序列上留下真实的空洞）。

```bash
$ ./chat_server -p 8901 --drop 30
$ ./chat_client -h 127.0.0.1 -p 8901 -n Carol
> /test 100
```

**客户端实测输出：**

```
[2026-11-04 13:19:11.xxx] 开始发送 100 条测试报文...
  ** 丢包告警: 服务端报文序号从 10 跳到 14, 中间丢失 3 帧 **
  ** 丢包告警: 服务端报文序号从 20 跳到 22, 中间丢失 1 帧 **

  ** 丢包告警: 服务端报文序号从 26 跳到 29, 中间丢失 2 帧 **
  ...
  ** 丢包告警: 服务端报文序号从 77 跳到 83, 中间丢失 5 帧 **

================= 丢包测试结果 =================
  发送测试报文数   : 100
  收到 ACK 数      : 62
  丢失报文数       : 38
  应用层丢包率     : 38.00 %

```

**交叉验证：** 两种**相互独立**的统计方法得到完全一致的结论——

| 统计方法 | 原理 | 丢失帧数 |
|----------|------|----------|
| ACK 计数法 | 发出 100 条测试报文，实收 62 个 ACK | **38** |
| 序号缺口法 | 由接收序号的最大空洞推算 | **38** |

二者一致说明丢包检测机制**准确无误**。注入丢包率 30%，实测 38%，偏差来源于
人工丢包是基于伪随机数的逐帧独立判定，样本量 100 时的统计波动。

### 5.5 测试三：客户端 → 服务端 方向丢包检测

反方向的检测由服务端完成。客户端加 `--drop 30` 丢弃自己发出的报文：

```bash
$ ./chat_server -p 8902                # 服务端不注入丢包
$ ./chat_client -h 127.0.0.1 -p 8902 -n Dave --drop 30
```

**服务端实测输出：**

**客户端同时收到服务端的可靠性告警：**

```
[2026-11-04 13:19:29.239] [可靠性] 服务端检测到你有 1 个报文丢失
```

**结论：** 双向丢包检测均正常工作。服务端不仅自己发现缺口，还通过 `LOSS_REPORT`

### 5.6 测试四：正常网络下的丢包观测

不注入丢包时（`--drop 0`），连续三轮 100 条测试报文：

```
================= 丢包测试结果 =================
  发送测试报文数   : 100
  收到 ACK 数      : 100
  丢失报文数       : 0
  应用层丢包率     : 0.00 %
==================================================
  发现的序号缺口数 : 0
  丢失报文总数     : 0
```

**观测结论（对应实验要求第 7 条）：**

1. 在 **TCP + 本机回环** 环境下，正常运行时**未观测到任何数据包丢失**，
   丢包率为 0.00%，序号缺口数为 0。这与 TCP 的可靠传输特性一致。

   > **注意**：这里的 `0.00%` 是**正确的观测值**，不是"没测出来"。
   > 丢包的**检测机制**（序号连续性比对）与丢包的**产生原因**是彼此独立的：
   > 检测代码始终在跑，它只是如实报告"没有观察到缺口"。
   > 传输层的丢包（重传后仍失败）在 TCP 之上本来就**不可能**被应用层看到——
   > 这正是实验要求第 7 条要观察的事实：**在可靠传输协议之上，应用层测不到丢包**。
   > 要在应用层制造并观测丢包，只能靠人为注入（见 5.4 / 5.5），
   > 而注入后同一套检测代码立刻报出 38% 且两种统计方法完全吻合，证明探测器有效。
2. 在**人工注入丢包**的条件下，检测机制能**准确、无遗漏地**识别出全部丢失帧
   （ACK 计数法与序号缺口法结果完全一致）。
3. 由此可得：**本协议提供了可靠的应用层丢包可观测能力**——在真实网络环境中，
   一旦发生丢包（物理链路故障、拥塞丢包、缓冲区溢出等），接收方能立即发现并精确量化。

## 六、调试中遇到的问题与解决

调试过程中发现并修复了若干**真实缺陷**，记录如下：

| # | 问题现象 | 原因分析 | 解决方法 |
|---|----------|----------|----------|
| 1 | 客户端退出时接收线程报 `接收出错: recv 失败` | 主线程直接 `close` 套接字，接收线程阻塞在 `recv` 上被强行中断 | 引入 `g_exiting` 标志区分"正常收尾"与"异常断连"；退出时先 `shutdown` 再 `close`，留 100ms 让接收线程自行退出 |
| 2 | 快速发送时服务端报 `头部行过长, 协议错误` | "头部过长"的长度检查错误地作用于**整个接收缓冲区**；当一次 `recv` 批量读到多个报文时缓冲区自然超过阈值 | 改为只在 `take_line()` **取不到换行符**时检查——此时整段缓冲区必然是不完整的头部行，检查才成立 |
| 3 | 注入丢包后接收方**完全看不到**任何异常 | 丢弃报文时**没有消耗序号**，序列仍然连续，缺口无从产生 | 改为**先分配序号再决定是否丢弃**，使丢弃在序号序列上留下真实空洞 |
| 4 | 注入丢包时 `/test` 统计丢包率为 0 | 丢包注入只作用于 `MSG_CHAT`，而测试的度量对象是服务端回发的 `MSG_ACK` | 将可丢弃报文类型扩展为 `MSG_CHAT` 与 `MSG_ACK`（数据类），控制类报文（登录/列表/心跳）始终送达以保证实验流程可继续 |
| 5 | 心跳线程与连接线程可能重复释放 `Client` 对象 | 双方各持裸指针 `Client*`，任一方 `delete` 后另一方即成悬垂指针 | 改用 `shared_ptr<Client>` 持有，线程参数传递 `shared_ptr` 副本，对象生命周期由引用计数保证 |
| 6 | 并发测试脚本误报大量消息丢失 | 测试用管道一次性喂完输入，客户端发完立即 `/quit`，三者**从未同时在线** | 重写为交互式测试：客户端保持在线、逐条交错发送、最后统一 `/quit` |
| 7 | 客户端 `/who` 命令无任何输出 | 客户端发的是 `PING` 报文，而服务端一律回 `PONG`，用户列表永远不会被下发 | 服务端约定：`PING` 载荷为 `"who"` 时改回 `USERLIST` 报文；客户端 `/who` 即发送该请求 |
| 8 | Windows 控制台输出中文与路径乱码 | 控制台代码页在 `print_usage()` **之后**才设置为 UTF-8；且 `argv[0]` 本身是 ANSI(GBK) 字节 | 把 `enable_utf8_console()` 提到 `main()` 开头；新增 `program_name()` 用 `GetCommandLineW()` 取宽字符命令行再转 UTF-8 |
| 9 | Windows 上测试脚本**静默跳过**（无任何输出即结束） | Windows 的 `python3` 是 Microsoft Store 的**空壳占位符**，执行后无输出且退出码为 0，被脚本误判为可用 | 探测时实际执行 `"$cand" -c "print('ok')"` 验证解释器真的能工作 |
| 10 | Windows 上丢包测试报 `Exec format error` | 脚本硬编码 `build/chat_server`，而 Windows 产物名为 `chat_server.exe` | 按 `uname -s` 判定平台并拼接 `.exe` 后缀（三个 shell 脚本统一处理） |
| 11 | **中文昵称乱码**：`chat_client.exe -n 张三` 显示为 `����` | Windows 的 `main()` 收到的 `argv` 是按系统 ANSI 代码页（中文系统 `ACP=936`，即 GBK）转换出来的字节：`张三` 在 `argv` 里是 `D5 C5 C8 FD`，而程序全链路按 UTF-8 处理，于是昵称被当成非法 UTF-8 序列显示为乱码。**消息正文不受影响**（正文走 socket 收发，是程序自己写的 UTF-8 字节） | 新增 `utf8_command_line()`：用 `GetCommandLineW()` 取未经 ANSI 转换的 Unicode 命令行，`CommandLineToArgvW()` 切分后逐个用 `WideCharToMultiByte(CP_UTF8, ...)` 转成 UTF-8。客户端与服务端的全部参数改用它解析 |
| 12 | 服务端启动行显示 `监听 r:8899`、客户端显示 `已连接到 :8899`（本该是 `0.0.0.0` 和 `127.0.0.1`），且夹杂**非法 UTF-8 字节** `C0 FB` | `log_line("...监听 %s:%d", host, port)` 中 `host` 是 `std::string`，却被当作 `char*` 交给 `%s`。MinGW TDM-GCC 的 libstdc++ 用的是旧式 COW `std::string`，对象起始处是 `_Rep` 的引用计数/长度字段而非字符数据，于是 `%s` 从对象首地址读出的是**指针字节**（本次实测为 `C0 FB 72`），属于非法 UTF-8，控制台渲染成替换字符 | 全部 `%s` 实参改为 `host.c_str()`；并用 `od -t x1` 复核输出字节，确认日志文件整体为合法 UTF-8 |
| 13 | **时间戳前偶发一个乱码方块**（形如 `[2026-11-04 15:38:49.412] [系统] Bob 加入了聊天室`，方块紧贴在 `[` 前面） | **不是编码问题，而是并发写 stdout**。客户端的主线程正在打印帮助文字与提示符 `> `，接收线程同时在打印带时间戳的消息；两者写的是同一个 stdout、共享同一个控制台光标，而光标是**唯一**的，于是两条输出会在行中间交错。实测用 `ReadConsoleOutputCharacterW` 转储屏幕缓冲区，捕获到 `U+FFFD count = 2`，且乱码恰好落在中文的**右半格**位置——控制台无法渲染半个汉字，只能输出替换字符 | 新增全局输出互斥锁 `g_out_mu` 与 `out_write()/out_printf()`：所有控制台输出（含提示符、帮助、统计块）**整段加锁**后再写出，保证一次输出在控制台上是原子的。服务端同样加锁（它有多个连接线程 + 心跳线程）。修复后复测 4 个窗口均为 `U+FFFD count = 0` |
| 14 | `/test [20]` 只发出 **1** 条测试报文（帮助里写的就是 `/test [n]`，用户照抄方括号即触发） | 参数解析用 `atoi(line.c_str() + 6)`，`atoi("[20]")` 遇到非数字字符 `[` 立即返回 **0**，`run_test()` 再把 0 钳成 1，于是只发 1 条——样本量过小，测出的丢包率 0.00% 没有意义 | 改为手写数字扫描：跳过空格与 `[` 再逐位取十进制数；`/test`、`/test 100`、`/test [100]`、`/test[100]` 均可。同时 `/nick <名字>` 也剥掉尖括号。实测 `/test [20]`→20 条、`/test 100`→100 条、`/test`→20 条 |
| 15 | `/ping` 的往返时延**恒为 0 ms**，看起来"网络没有延迟"或"没测出来" | 计时用的是 `GetSystemTimeAsFileTime()`。它的"100 ns"只是 FILETIME 的**数值单位**，实际刷新粒度由系统时钟节拍决定（典型 **15.6 ms**），连续两次读取常常拿到同一个值，差值恒为 0——**与真实的网络延迟无关**。而本机回环的真实 RTT 只有 0.2~0.5 ms，本来就不足 1 ms | 新增 `now_us()`，采用**双时钟对齐**：启动瞬间用 FILETIME 取一次墙上时钟作基准，之后用 `QueryPerformanceCounter`（硬件计时器，实测分辨率约 1 µs）的单调增量推进。PING/PONG 载荷改用**微秒**时间戳，输出 `RTT = 494 us (0.494 ms)`。实测同机回环稳定在 200~500 µs，与"两次内核 TCP/IP 栈往返 + 两次线程唤醒 + 业务处理"的量级估算吻合 |
| 16 | 演示运行期间执行 `build.bat` 报 `ld.exe: cannot open output file build\chat_server.exe: Permission denied` | 正在运行的 exe 是**内存中的映像文件**，Windows 不允许覆盖它（可写但不可覆盖），链接器因此失败。这不是权限或路径问题，而是"演示进程占着 exe" | `build.bat` 改为**先编译到 `*.new.exe`，再换名替换**：把旧 exe `move` 成 `*.old.exe`（改名正在运行的映像是允许的），再把新 exe 移到位，最后尝试删除 `*.old.exe`（删不掉说明旧进程还在跑，下次构建会清掉）。`test/run_all.sh` 用同样的换名逻辑，因此**可以在演示运行期间跑测试**。实测：演示服务器占用 `build\chat_server.exe` 的情况下，`build.bat` 与 `bash test/run_all.sh` 均成功，四项测试全部通过 |
| 17 | 服务器窗口只记录"谁登录了"，**看不到谁离开了**；客户端被强杀时更是毫无记录，只留下一行 `读取报文失败: recv 失败` | `broadcast()` 只负责发帧、**不打印日志**，所以"离开"通知虽然确实广播给了其他客户端，却从未出现在服务器窗口上；同时 `recv` 失败被笼统地报成"recv 失败"，读者会误以为是程序 bug 而不是"对端进程被杀" | 连接对象新增 `quit_req` 标志区分正常/异常退出；收尾时对异常断开补打一行 `用户 X(id=N) 断开连接, 已从用户表移除`（主动 `/quit` 的不重复记录）。同时 `net_io.cpp` 新增 `recv_error_text()`，把 `WSAECONNRESET` 翻译成 `连接被对端重置(异常断开)`，把 `WSAECONNABORTED` 翻译成 `连接被中止` |
| 18 | `/nick` 改名后，所有人看到的却是 **"[系统] X 加入了聊天室"**，服务器日志也重新打了一遍"用户 X(id=N) 登录成功"，一次改名被当成了新上线 | 客户端的 `/nick` 复用了 `LOGIN_REQ` 报文来传新昵称。而 `LOGIN_REQ` 在服务端的语义是"建立会话并分配身份"，处理它必然伴随"登录成功"日志 + "加入了聊天室"广播 + 在线列表全量更新。**改名与登录是两种不同的语义，不该共用同一种报文** | 新增两个报文类型：`NICK_CHANGE`（C→S，请求改名）与 `NICK_ACK`（S→C，改名结果）。客户端改用 `NICK_CHANGE`，且**不立即改本地昵称**，等服务端 `NICK_ACK` 回来再回填，避免两端状态不一致；服务端用独立的 `apply_nick_change()` 处理，日志只记一条 `用户 旧名(id=N) 将昵称改为 新名`，其他人收到的是"改名"通知而不是"加入"通知。另外，服务端对**已登录**连接再次收到 `LOGIN_REQ` 时也按改名处理，杜绝旧版客户端再触发这个语义错误 |
| 19 | 客户端输入 `ping` 后，**所有用户的窗口**都出现了 `[时间] pc3: ping` 这条聊天消息，而发起者自己反而看不到想看的往返时延 | 客户端把 `ping` 当成普通聊天消息发了出去。根因有两层：(1) 用户漏写了命令前缀 `/`，客户端对“少了 '/' 的输入”只打印一句提示、**仍然按聊天消息原样发送**，于是 `ping` 被服务端 `broadcast()` 广播给所有人；(2) 客户端的命令解析与聊天发送逻辑**混在同一个 `if` 分支里**，内建命令没有独立出口，导致“命令”和“聊天”两种语义无法区分 | 把客户端的命令处理从 `handle_input()` 中**抽出为独立的 `exec_command()`**，使内建命令拥有自己的出口：命令一律**就地执行、不走聊天广播**，因此无论带不带 `/`，`ping` 的探测过程与往返时延都**只有使用者本人可见**。新增 `parse_bare_command()` 识别漏写 `/` 的命令（`ping`/`who`/`stat`/`help`/`quit`/`exit`/`test <数字>`/`nick <名字>`），匹配成功则补上 `/` 后执行，并提示“已按 /ping 执行(该命令仅你自己可见, 不会广播给他人)”；为避免误伤正常聊天，识别要求**命令形式完整合法**——`ping 你好吗`、`test message one` 这类句子仍按聊天消息发送。服务端对应处补一行日志 “收到 X(id=N) 的 ping 探测, 已单播回送 PONG(不广播)”，便于演示时在服务器窗口佐证未广播。实测：发起者窗口显示 `Pong: 往返时延 RTT = 583 us (0.583 ms)`，旁观者窗口**完全没有** ping 的痕迹 |

## 七、实验结论

1. **协议设计**：CHT/1.0 采用「ASCII 头部 + 定长主体 + CRC32」结构，
   通过长度字段解决 TCP 流式无边界问题，通过 UTF-8 与字节长度解决中英文混排问题，
   通过单调序号解决丢包可观测问题，通过 `TS` 字段与"转发保留原始时间"的约定解决时间语义问题。
2. **程序实现**：完全基于原生 Socket 函数编写，未使用任何封装类库；
   采用"每连接一线程 + 发送锁 + 快照遍历"的多线程模型，支持多人同时聊天。
3. **中英文支持**：实测中英文混合消息在三人同时在线时全部正确送达，无乱码、无截断。
   为此专门做了两道验证：一是把 stdout 重定向到文件后用 `od` 核对**字节流**本身是合法 UTF-8；
   二是用 `ReadConsoleOutputCharacterW` 直接转储**真实控制台屏幕缓冲区**，统计替换字符 `U+FFFD` 的个数，
   修复前为 2、修复后为 0——确认"控制台里看得见的乱码"与"协议里传的数据"是两回事。
4. **丢包观测**：正常网络下丢包率为 0.00%；注入丢包后两种独立统计方法均精确得出相同的丢失帧数
   （实测 38 帧），检测机制准确有效，
   且双向（客户端侧与服务端侧）均能检测并相互告警。
5. **程序质量**：8 个文件 2068 行左右，职责划分清晰，
   `-Wall -Wextra` 零警告，关键并发点均有明确的锁保护与注释说明；
   另提供 `build.bat` 一键编译与 `demo.bat` 一键线下演示（服务器 + 3 客户端窗口）。
6. **时延测量**：用 `QueryPerformanceCounter` 硬件计时器测得同机回环 RTT 为 **0.2~0.5 ms**，
   与"两次内核 TCP/IP 栈往返 + 两次线程唤醒 + 业务处理"的量级估算一致；
   同时澄清了"同一台机器为何还有时延"——回环是虚拟网卡，数据仍走完整网络栈，
   并非"零成本"。
7. **用户动态增减**：实测 12 人接入 → 强杀 5 人（异常掉线）→ 列表正确收缩为 7 人
   → 再补 3 人 → 正确增长为 10 人；新加入者发言被**全部 10 个客户端**收到。
   用户表由互斥量保护、广播前先做 `shared_ptr` 快照（持锁不做 I/O），
   正常退出与异常掉线两条路径收敛到同一段收尾逻辑，在线列表始终正确。
