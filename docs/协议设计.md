# CHT/1.0 聊天协议设计说明书

> 传输层：TCP（流式 Socket，面向字节流，无消息边界）
> 字符集：全部文本字段均为 UTF-8，中文直接以多字节形式承载，无需转义

---

## 一、设计目标与约束

| 需求 | 协议层面的应对 |
|------|---------------|
| 聊天信息带时间 | 头部行含 `TS` 字段（Unix 毫秒时间戳），服务端转发时保留**原始发送时间**，保证群聊中各端显示的时间一致 |
| 流式 Socket | 报文带**定长字段**（`SENDER_LEN`/`PAYLOAD_LEN`），接收方据此从字节流中切分报文；不依赖 `recv` 一次返回一整包 |
| 支持中文/英文 | UTF-8 编码；长度按**字节数**计算而非字符数，中文与英文在同一字段中等价处理 |
| 支持多人聊天 | `MSG_CHAT` 采用**广播**语义；`MSG_USERLIST` 同步在线成员 |
| 可检测丢包 | 每条报文带**单调递增序号** `SEQ`，接收方比对序号连续性即可发现丢失 |
| 抗数据损坏 | 报文尾部带 **CRC32** 校验，覆盖昵称与负载 |

---

## 二、报文总体结构

一帧报文由三段组成，顺序固定：

```
┌──────────────────────────────────────────────┐
│ ① 头部行 (ASCII, 以 '\n' 结束, 变长)          │
├──────────────────────────────────────────────┤
│ ② 发送者名 SENDER  (SENDER_LEN 字节, UTF-8)   │
├──────────────────────────────────────────────┤
│ ③ 负载 PAYLOAD   (PAYLOAD_LEN 字节, UTF-8)    │
├──────────────────────────────────────────────┤
│ ④ CRC32          (4 字节, 大端序)             │
└──────────────────────────────────────────────┘
```

### 2.1 头部行语法

```
CHT1 <TYPE> <SEQ> <TS> <SENDER_LEN> <PAYLOAD_LEN>\n
```

用 BNF 描述：

```
header-line  ::= "CHT1" SP type SP seq SP ts SP sender-len SP payload-len LF
type         ::= DIGIT+              ; 报文类型, 见 §3
seq          ::= DIGIT+              ; 序号, 从 1 开始逐条递增
ts           ::= DIGIT+              ; Unix 毫秒时间戳 (UTC)
sender-len   ::= DIGIT+              ; SENDER 字节数, 上限 64
payload-len  ::= DIGIT+              ; PAYLOAD 字节数, 上限 8192
LF           ::= 0x0A
```

**为什么头部用 ASCII 而不用二进制？** 头部用文本便于用 `telnet`/`nc` 抓包肉眼观察，且长度字段以十进制表示便于手工构造测试报文；同时头部与负载物理分离，中文负载可以任意包含 `\n`、空格等字符而不破坏帧结构。

### 2.2 主体长度与切帧规则

```
主体总长 = SENDER_LEN + PAYLOAD_LEN + 4
```

接收方处理步骤：

1. 从字节流中读出**直到第一个 `\n`** 的内容作为头部行（`\r\n` 结尾时去掉 `\r`）；
2. 解析头部，得到 `SENDER_LEN`、`PAYLOAD_LEN`；
3. 继续从字节流中读**恰好** `SENDER_LEN + PAYLOAD_LEN + 4` 字节为主体；
4. 切分：前 `SENDER_LEN` 字节为昵称，其后 `PAYLOAD_LEN` 字节为负载，最后 4 字节为 CRC32；
5. 计算 `CRC32(SENDER || PAYLOAD)` 与帧尾 CRC32 比较，不一致则丢弃该帧并告警。

> **关键点**：TCP 无消息边界，一次 `recv` 可能只返回半条报文，也可能返回多条报文。
> 因此接收端必须维护**接收缓冲区**，先切出完整帧再解析，剩余字节留给下一帧。
> 本程序 `net_io.cpp` 中的 `Conn::rbuf` 即承担此职责。

## 三、报文类型（语义定义）

| TYPE | 名称 | 方向 | 负载含义 | 语义 |
|------|------|------|----------|------|
| 1 | `LOGIN_REQ` | C→S | 昵称（UTF-8） | 客户端请求登录。必须是连接上的**第一帧**。昵称为空则由服务端按连接顺序分配 `pc<id>`（即 `pc1` / `pc2` / `pc3` …） |
| 2 | `LOGIN_ACK` | S→C | 欢迎语（含分配的用户编号与用户名） | 服务端确认登录成功，并同时告知用户编号与最终生效的用户名。格式固定为 `登录成功, 你的用户编号是 <id>, 用户名是 <nick>`，客户端据此回填本端昵称 |
| 3 | `LOGOUT` | C→S | 空 | 客户端主动下线。服务端广播下线通知后关闭连接 |
| 4 | `CHAT` | 双向 | 聊天正文（UTF-8） | 群聊消息。服务端广播给**所有**在线用户（含发送者本人） |
| 5 | `SYSTEM` | S→C | 提示文本 | 系统通知：有人加入/离开、参数错误等 |
| 6 | `USERLIST` | S→C | 昵称列表，`\|` 分隔 | 在线用户列表，任何成员变化时广播 |
| 7 | `PING` | 双向 | 时间戳字符串 | 心跳探测；用于测量 RTT、探测失联连接。载荷为 **Unix 微秒时间戳**（十进制字符串），PONG 原样回显。**点对点**处理：服务端只把 PONG 回送给发起方，绝不转发给其他用户 |
| 8 | `PONG` | 双向 | 回显 PING 的载荷 | 心跳应答。**点对点**处理，只有发起方会收到 |
| 9 | `ACK` | S→C | 被确认帧的序号 | 应用层确认，用于统计请求-应答成功率 |
| 10 | `LOSS_REPORT` | S→C | 缺失报文个数 | 服务端告知客户端"你丢失了 N 个报文" |
| 11 | `NICK_CHANGE` | C→S | 新昵称（UTF-8） | 客户端请求修改昵称。**控制类报文**，不广播加入/离开，只触发一条改名通知 |
| 12 | `NICK_ACK` | S→C | 生效的新昵称 | 服务端确认改名结果。载荷为空表示被拒绝（如昵称为空） |

### 3.1 两种特殊负载约定

- **测试报文**：负载以 `TEST:` 开头（如 `TEST:37`）的 `CHAT` 帧被视为可靠性测试报文。
  服务端**不广播**，只回一帧 `ACK`（载荷为该测试帧的 `SEQ`），从而可精确统计往返成功率。
- **用户列表**：载荷以 `|` 分隔的昵称，如 `pc1|pc2|pc3`。

### 3.2 报文的"可见范围"（点对点 vs 广播）

协议区分两类语义：

| 类别 | 报文 | 可见范围 |
|------|------|----------|
| **广播** | `CHAT`、`SYSTEM`、`USERLIST` | 服务端转发给**所有**在线用户（含发送者本人） |
| **点对点** | `PING`、`PONG`、`ACK`、`LOSS_REPORT`、`NICK_ACK`、`LOGIN_ACK` | 只发给**发起方那一条连接**，其他用户完全看不到 |

因此 `/ping` 的探测过程与往返时延**只有使用者本人可见**：

```
客户端 A                服务端                客户端 B
   |  PING(微秒时间戳)   |                      |
   |------------------->|  (不广播给 B)        |
   |                    |                      |
   |<-------------------|  PONG(回显载荷)      |
   |  本地打印 RTT       |                      |
   |                    |   B 的窗口: 无任何痕迹 |
```

客户端侧的**内建命令**（`/ping`、`/who`、`/stat`、`/test`、`/nick`、`/help`、`/quit`）
一律是**本端行为**：命令本身不会被当成聊天消息发送，其输出也只打印在使用者的窗口里。

## 四、时序（Sequence / Timing）

### 4.1 登录与群聊时序

```
客户端A              服务端                客户端B
   |                    |                     |
   |-- LOGIN_REQ(昵称) -->|                     |
   |<-- LOGIN_ACK ------|                     |
   |<-- SYSTEM(加入) ---|                     |
   |<-- USERLIST -------|--> USERLIST ------>|   (广播给所有人)
   |                    |                     |
   |-- CHAT("你好") ---->|                     |
   |<-- CHAT(时间戳) ---|                     |
   |                    |--- CHAT(时间戳) --->|   (转发给所有在线用户)
   |                    |                     |
   |-- PING(t) --------->|                     |
   |<-- PONG(t) --------|                     |   (RTT = now - t)
   |                    |                     |
   |-- LOGOUT ---------->|                     |
   |                    |--- SYSTEM(离开) --->|
   |<-- 连接关闭 --------|                     |
```

### 4.2 时间戳语义（关键约定）

- `TS` 记录的是**消息产生时刻**，而非转发时刻。
- 服务端转发 `CHAT` 时**原样保留客户端填入的 `TS`**，因此群聊中所有参与者看到的时间戳完全相同，
  便于讨论"谁在什么时候说了什么"。
- `SYSTEM` / `USERLIST` / `LOGIN_ACK` 等服务端产生的报文，`TS` 为服务端生成时刻。

### 4.3 序号语义

- 序号 `SEQ` 的作用域是**一条连接**，由发送方维护，从 1 开始逐条 +1，**不回绕**。
- 发送方保证"分配序号"与"写帧"原子化（同一把互斥锁保护），因此接收方看到的序号**单调递增且无空洞**（除非发生丢包）。
- 服务端对**每个客户端分别**维护一个发往该客户端的序号计数器，因为不同客户端收到的帧集合不同。

### 4.4 丢包检测时序

```
发送端:  帧1(seq=1) 帧2(seq=2) [帧3(seq=3) 丢失] 帧4(seq=4)
接收端收到:  seq=1    seq=2            seq=4
                    ↑ 期望 seq=3, 实际 seq=4 → 判定丢失 1 帧
```

判据：`recv_seq > last_recv_seq + 1` ⇒ 丢失 `recv_seq - last_recv_seq - 1` 帧。

本协议在**两个方向**都实现了该检测：

| 方向 | 检测方 | 实现位置 | 现象 |
|------|--------|----------|------|
| C→S | 服务端 | `server.cpp: check_seq()` | 服务端打印"检测到用户 X 丢失 N 个报文"，并向该客户端下发 `LOSS_REPORT` |
| S→C | 客户端 | `client.cpp: check_seq()` | 客户端打印"丢包告警: 服务端报文序号从 a 跳到 b" |

## 五、异常与错误处理

| 场景 | 处理策略 |
|------|----------|
| 头部魔数不是 `CHT1` | 判定为协议错误，断开连接 |
| `SENDER_LEN`/`PAYLOAD_LEN` 越界 | 协议错误，断开连接（防越界/防内存膨胀） |
| 头部行长度超过 `MAX_HEADER_LEN`(128) | 协议错误，断开连接 |
| CRC32 不匹配 | 丢弃该帧并记录错误（数据在传输中被破坏） |
| 未登录就发 `CHAT` | 回 `SYSTEM` 提示，不广播 |
| 对端异常断开 | `recv` 返回 0，连接线程收尾，广播下线通知 |
| 长时间无任何活动（>120s） | 心跳线程 `shutdown` 该连接并清理 |

## 六、协议的可扩展性

- **新增类型**：只需在 `protocol.h` 的 `MessageType` 枚举中增加取值，其余代码路径不变；
- **新增字段**：追加在头部行末尾并同步修改 `parse_header_line()`，版本号可升为 `CHT2`；
- **点对点私信**：可复用 `CHAT`，在负载中加 `目标昵称` 前缀，由服务端识别后单播。
- **加密**：可在 `CRC32` 之前插入密文段，或直接对负载做 TLS/对称加密。

## 七、PING / PONG 为什么用微秒时间戳

`PING` 的载荷是发送时刻的 **Unix 微秒时间戳**，`PONG` 原样回显，接收方用
`now_us() - 载荷` 得到往返时延 RTT。

**为什么不用毫秒？** 本机回环上的真实 RTT 只有 **0.2 ~ 0.5 ms**，用整数毫秒显示
就恒为 `0 ms`，演示时看不出任何差别，也容易被误认为"没测出来"。

**为什么不用 `GetSystemTimeAsFileTime` 直接换算微秒？** 因为它的"100 ns"只是
**数值单位**，实际刷新粒度由系统时钟节拍决定（典型 **15.6 ms**），连续两次读取
往往拿到同一个值，差值恒为 0。

因此 `protocol.cpp` 中的 `now_us()` 采用**双时钟对齐**：

```
启动瞬间:  FILETIME  ──→  unix_us   (墙上时钟基准)
           QPC      ──→  qpc        (高精度单调计数器基准)
此后每次:  now_us = unix_us + (QPC_now - qpc) 换算成微秒
```

`QueryPerformanceCounter` 是硬件计时器，实测分辨率约 1 µs，既保持了正确的
Unix 时间语义，又能分辨出微秒级间隔。详见实验报告 §6 第 15 条。
