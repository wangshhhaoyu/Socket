## 二、各模块职责

### 2.1 协议模块 `protocol.h` / `protocol.cpp`

| 项目 | 说明 |
|------|------|
| 职责 | 报文类型定义、帧的编码与解码、CRC32 校验、时间戳格式化 |
| 关键函数 | `encode_message()` 报文→字节串<br>`decode_message()` 字节串→报文<br>`parse_header_line()` 仅解析头部（流式读取时先取长度）<br>`crc32()` 校验和<br>`now_ms()` / `format_time()` 时间工具 |
| 数据结构 | `struct Message { type; seq; ts_ms; sender; payload; }` |
| 关键约束 | 昵称 ≤ 64 字节，负载 ≤ 8192 字节，头部行 ≤ 128 字节 |
| 设计要点 | 头部与负载**物理分离**，长度字段驱动切帧，因此负载可含任意 `\n` 与中文多字节字符 |

### 2.2 网络 I/O 模块 `net_io.h` / `net_io.cpp`

| 项目 | 说明 |
|------|------|
| 职责 | 在裸 socket 之上实现"按协议帧读写"，处理 TCP 流式特性 |
| 关键函数 | `conn_read_frame()` 从字节流切出完整一帧<br>`conn_write_frame()` 加写锁整帧写出<br>`create_listen_socket()` / `create_connect_socket()` 建连 |
| 数据结构 | `struct Conn { fd; send_mu; rbuf; }` — `rbuf` 为接收缓冲区，保存已到达但未成帧的字节 |
| 关键约束 | 写操作必须整帧加锁；读操作必须先凑齐整帧 |
| 设计要点 | **不使用任何现成 Socket 类库**，仅用 `socket/bind/listen/accept/connect/send/recv` 原生函数 |

### 2.3 会话管理模块（服务端）

| 项目 | 说明 |
|------|------|
| 职责 | 维护在线用户表，处理登录/登出，分配用户编号 |
| 关键数据结构 | `vector<shared_ptr<Client>> g_clients` + `mutex g_clients_mu` |
| 关键操作 | `build_user_list()` 生成在线列表；`broadcast_user_list()` 同步列表 |
| 并发要点 | 表格加锁保护；线程持有 `shared_ptr<Client>`，避免心跳线程与连接线程互相释放对象导致悬垂指针 |

### 2.4 转发模块（服务端）

| 项目 | 说明 |
|------|------|
| 职责 | 将消息广播给所有在线用户；推送系统通知与用户列表 |
| 关键函数 | `broadcast(type, payload, ts, sender)` 群发；`send_frame()` 单发 |
| 并发要点 | 每条连接有独立 `send_mu`，保证"分配序号 + 写帧"原子化，序号单调无空洞 |

### 2.5 可靠性模块（双端）

| 项目 | 说明 |
|------|------|
| 职责 | 通过序号连续性检测丢包；统计丢包率；可选人工注入丢包 |
| 关键函数 | `check_seq()` 序号缺口判定；`run_test()` 发送测试报文并统计 ACK 到达率 |
| 关键数据 | `g_gap_count`（缺口次数）、`g_gap_msgs`（丢失帧总数）、`g_ack_count`（ACK 数） |
| 关键设计 | **丢弃报文时必须先消耗序号**，否则接收方看不到空洞，检测机制形同虚设 |

### 2.6 心跳模块（服务端）

| 项目 | 说明 |
|------|------|
| 职责 | 周期性向客户端发 `PING`，回收失联连接 |
| 关键实现 | 独立线程，每 5 秒一轮；客户端超过 120 秒无活动则 `shutdown` 连接 |

### 2.7 命令模块（客户端）

| 命令 | 功能 |
|------|------|
| 直接输入文字 | 发送聊天消息（支持中英文） |
| `/nick <名字>` | 修改昵称（服务端记录一条独立日志并广播改名通知） |
| `/who` | 查看在线用户列表 |
| `/ping` | 发送心跳并测量 RTT |
| `/test [n]` | 发送 n 条测试报文，统计应用层丢包率 |
| `/stat` | 显示收发统计与丢包情况 |
| `/quit` | 退出聊天 |

## 四、并发设计小结

| 并发点 | 保护措施 |
|--------|----------|
| 多个线程向**同一连接**写帧 | 每连接一把 `send_mu`，且"分配序号+写帧"在同一临界区内 |
| 多线程读写**在线用户表** | 全局 `g_clients_mu`；操作采用"加锁拷贝快照 → 锁外遍历"避免长时间持锁 |
| 心跳线程与连接线程共享 `Client` | 用 `shared_ptr<Client>` 持有，线程结束前对象不会被释放 |
| 客户端**收发**并行 | 接收线程 + 主线程分离；发送侧用 `g_send_mu` 保护序号分配 |
| 客户端**退出**与接收线程 | `g_exiting` 标志区分"正常收尾"与"异常断连"；先 `shutdown` 再 `close` |

**为什么服务端用"每连接一线程"而不是线程池？**

聊天服务器的主要开销在**网络 I/O 等待**而非计算，每个连接一个阻塞线程可以让代码结构极其直观
（一个连接的全部状态与处理逻辑集中在一个函数内），这正是本实验强调"结构清晰、可读性好"的要求。
若要支持上万并发，可改为 `select`/`epoll` 事件驱动或线程池 + 队列，本程序的协议层与转发层无需改动。
