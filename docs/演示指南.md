# 线下演示指南

本文是**现场演示的操作手册**。所有输出均为实测抓取，可直接对照讲解。
演示环境：Windows 11 + MinGW-w64 (TDM-GCC 5.1.0)。

---

## 零、演示前 5 分钟准备

### 1. 编译

```bat
build.bat
```

预期输出：

```
[1/2] compiling chat_server.exe ...
[2/2] compiling chat_client.exe ...
[OK] build complete: build\chat_server.exe  build\chat_client.exe
```

### 2. 确认编译器在 PATH 中

演示机若未装 MinGW，下载 [MinGW-w64](https://www.mingw-w64.org/downloads/)，
安装后把其 `bin` 目录加入系统 `PATH`，然后重开命令行。

> `build.bat` 会先检测 `g++`，找不到就直接报错退出，不会生成半成品。

### 3. 建议的窗口布局

演示时开 **4 个命令行窗口**，用 Win+← / Win+→ 分屏平铺：

```
┌──────────────┬──────────────┐
│  CHT-Server  │  CHT-pc1     │
│  (服务器)     │  (客户端)     │
├──────────────┼──────────────┤
│  CHT-pc2     │  CHT-pc3     │
└──────────────┴──────────────┘
```

Windows Terminal 可用标签页平铺；或直接用 `demo.bat` 自动开好 4 个窗口再手动排版。

## 一、一键拉起（最快路径）

```bat
demo.bat
```

自动打开 4 个窗口：服务器 + pc1 / pc2 / pc3（客户端不传 `-n`，昵称由服务器按连接顺序分配）。
**不需要**手工敲任何命令，开场即可聊天。

## 二、分段演示脚本

### 环节 1：登录与在线列表（约 30 秒）

**演示点**：多人同时在线、在线列表实时同步、**用户编号与用户名同时分配**。

`demo.bat` 启动的三个客户端**不传 `-n`**，因此由服务器按连接顺序自动分配
`pc1` / `pc2` / `pc3`。在 pc1 窗口输入：

```
/who
```

预期输出：

```
> (等待服务器返回在线用户列表...)
> [2026-11-04 17:05:04.097] [在线用户] pc1|pc2|pc3
```

**讲解词**：
> 每个人登录时服务器分配一个唯一编号，并实时把在线成员列表广播给所有人。
> 刚才三个客户端几乎同时接入，列表从 `pc1` 逐步变成 `pc1|pc2`、`pc1|pc2|pc3`，
> 说明三人确实同时在线，而不是串行登录。
>
> 登录应答把**编号和用户名一起**给了：`登录成功, 你的用户编号是 1, 用户名是 pc1`。
> 用户名没指定时由服务器按连接顺序分配 `pc1/pc2/pc3`；
> 用 `-n 张三` 指定，就用你给的名字 —— 这也是下面环节 2b 的内容。

**可补一句**（切到服务器窗口展示日志）：

```
[2026-11-04 17:05:00.564] 服务器已启动, 监听 0.0.0.0:8914 (人工丢包率=0%)
[2026-11-04 17:05:01.776] 新连接: fd=368, 分配 id=1
[2026-11-04 17:05:01.776] 连接线程启动: fd=368
[2026-11-04 17:05:01.778] 用户 pc1(id=1) 登录成功
[2026-11-04 17:05:02.889] 新连接: fd=400, 分配 id=2
[2026-11-04 17:05:02.889] 连接线程启动: fd=400
[2026-11-04 17:05:02.891] 用户 pc2(id=2) 登录成功
[2026-11-04 17:05:04.095] 新连接: fd=384, 分配 id=3
[2026-11-04 17:05:04.095] 连接线程启动: fd=384
[2026-11-04 17:05:04.096] 用户 pc3(id=3) 登录成功
```

> 每个连接一个独立线程（`连接线程启动: fd=xxx`），所以新增用户不会阻塞已有用户。

### 环节 2：中英文混合聊天（约 1 分钟）

**演示点**：中英文混合、消息带时间戳、广播给所有人（含发送者本人）。

在 pc1 窗口依次输入：

```
Hello everyone, this is pc1.
大家好，我是pc1，中文测试！
```

切到 pc2 窗口，预期看到：

```
[2026-11-04 17:05:28.668] pc1: Hello everyone, this is pc1.
[2026-11-04 17:05:28.668] pc1: 大家好，我是pc1，中文测试！
```

再在 pc2 窗口输入：

```
Hi pc1! Nice to meet you.
Bob here. 你好啦！
```

pc1 窗口立刻出现：

```
[2026-11-04 17:05:29.793] pc2: Hi pc1! Nice to meet you.
[2026-11-04 17:05:29.793] pc2: Bob here. 你好啦！
```

**讲解词**：
> 每条消息前都有毫秒级时间戳 `[2026-11-04 17:05:29.793]`，时间由**发送方**在报文头里给出，
> 服务器转发时**原样保留**，所以所有人看到的时间完全一致——不是各收各的时间。
>
> 中文和英文走的是同一条路径：协议里所有文本都是 UTF-8，长度按**字节**算，
> 中文一个字占 3 字节、英文一个字符占 1 字节，在协议层是同等的，不需要任何转义或特殊处理。

### 环节 2b：中文昵称（建议加演，30 秒）

**演示点**：中文不只是消息正文能用，**昵称**也能是中文；并且能覆盖服务器的默认昵称。

手动新开一个客户端窗口：

```bat
build\chat_client.exe -h 127.0.0.1 -p 8888 -n 张三
```

预期输出（**昵称正常显示，不乱码；编号与用户名一起给出**）：

```
> [2026-11-04 15:21:06.403] 登录成功, 你的用户编号是 4, 用户名是 张三
[2026-11-04 15:21:06.403] [系统] 张三 加入了聊天室
[2026-11-04 15:21:06.403] [在线用户] pc1|pc2|pc3|张三
```

在已有客户端执行 `/who`，同样能看到 `张三`；张三发消息时其他人看到的是 `张三: 内容`。

**讲解词**（若评委追问中文乱码问题，这段很关键）：
> 这里踩过一个坑：Windows 上 `main()` 收到的 `argv` 是按系统 ANSI 代码页转换的字节，
> 中文系统是 GBK，`张三` 在 `argv` 里其实是 `D5 C5 C8 FD`，按 UTF-8 解释就成乱码了。
> 所以命令行参数改用 `GetCommandLineW()` 取 Unicode 命令行，
> 再用 `CommandLineToArgvW()` 切分、逐个转 UTF-8 ——
> **正文走 socket、参数走命令行，是两条不同的编码路径，两边都要各自处理**。

**可现场验证字节等价**：切到 pc1 窗口执行 `/stat`，看序号连续、无缺口。

### 环节 2c：用户动态增减（建议加演，1 分钟）

**演示点**：聊天室是**动态**的——随时可以有人进来、有人离开，在线列表实时同步。

**加**：另开一个客户端窗口（不传 `-n`）：

```bat
build\chat_client.exe -h 127.0.0.1 -p 8888
```

pc1 窗口立刻出现：

```
[2026-11-04 17:31:02.115] [系统] pc4 加入了聊天室
[2026-11-04 17:31:02.116] [在线用户] pc1|pc2|pc3|pc4
```

**减（正常退出）**：在该窗口输入 `/quit`，其余窗口出现：

```
[2026-11-04 17:31:20.884] [系统] pc4 离开了聊天室
[2026-11-04 17:31:20.885] [在线用户] pc1|pc2|pc3
```

**减（异常掉线）**：直接关掉那个窗口（不用 `/quit`），
其余窗口同样会看到"离开了聊天室"和收缩后的列表：

```
[2026-11-04 17:31:35.402] [系统] pc4 离开了聊天室
[2026-11-04 17:31:35.403] [在线用户] pc1|pc2|pc3
```

服务器窗口同时留痕：

```
[2026-11-04 17:31:20.884] 用户 pc4(id=4) 主动退出
[2026-11-04 17:31:35.401] 读取报文失败: 连接被对端重置(异常断开)
[2026-11-04 17:31:35.402] 用户 pc4(id=4) 断开连接, 已从用户表移除
```

**讲解词**：
> 用户表由一把互斥量保护，新增用户时插入、离开时摘除，并**全量广播**一次最新列表，
> 所以每个人的列表始终一致，不需要谁去"查询"。
>
> 广播时先把用户列表**快照**一份再释放锁，然后逐个发送 ——
> 这样持锁期间不做 I/O，一个网络慢的用户不会拖住其他人。
>
> 用户编号 `id` 是**唯一且永不复用**的，昵称只是显示名，允许重名。
> 这就是为什么登录应答要"编号和用户名一起给"：
> 列表里如果有两个 `Alice`，看编号才能分清是谁。

### 环节 3：消息格式（体现"时间在报文里"）

**演示点**：让评委看到协议不是靠时间戳字符串后缀拼的，而是**报文头的一部分**。

打开 `docs/协议设计.md`，指着帧结构图讲：

```
┌──────────────────────────────────────────────┐
│ ① 头部行 (ASCII, 以 '\n' 结束)                │
│    CHT1 <TYPE> <SEQ> <TS> <SENDER_LEN> <PAYLOAD_LEN>\n
├──────────────────────────────────────────────┤
│ ② SENDER  (SENDER_LEN 字节, UTF-8)            │
├──────────────────────────────────────────────┤
│ ③ PAYLOAD (PAYLOAD_LEN 字节, UTF-8)           │
├──────────────────────────────────────────────┤
│ ④ CRC32    (4 字节, 大端序)                   │
└──────────────────────────────────────────────┘
```

**讲解词**：
> `TS` 是头部行的一个独立字段，和 `TYPE`、`SEQ` 同级，不是拼在消息文本里的。
> `SENDER_LEN` 和 `PAYLOAD_LEN` 让接收方能从字节流里精确切出主体——
> 这就是应对"TCP 是字节流、没有消息边界"的办法。
> 尾部 CRC32 覆盖 SENDER+PAYLOAD，用于校验完整性。

**若要现场抓包**：用 Wireshark 抓 `127.0.0.1:8888`，按 ASCII 过滤 `CHT1`，
即可看到逐字节的头部行 —— 因为头部刻意设计成 ASCII 的，就是为了可读、可抓包核对。

### 环节 4：往返时延与在线状态（约 30 秒）

**演示点**：心跳机制、连接健康度。

在任一客户端输入：

```
/ping
```

预期输出：

```
> [2026-11-04 17:17:28.268] Pong: 往返时延 RTT = 494 us (0.494 ms)
```

**讲解词**：
> 客户端发 PING，服务端回 PONG，带回客户端的时间戳，客户端算出往返时延。
> 服务器后台还有心跳线程，定期探测所有连接，超时未响应就自动回收——
> 这就是长时间演示时不会留下"僵尸用户"的原因。

**补充演示：ping 是"私有"的**

在客户端 A 输入 `/ping`（或直接输入 `ping`，漏写 `/` 也能识别），
观察**其它客户端窗口完全没有变化** —— 既看不到 `ping` 这条指令，
也看不到往返时延的数字。服务器窗口会留下一行佐证：

```
[2026-11-04 19:09:54.799] 收到 pc1(id=2) 的 ping 探测, 已单播回送 PONG(不广播)
```

**讲解词**：
> PING/PONG 是协议里的**点对点**报文，服务端只把应答回送给发起方那一条连接，
> 不做广播；同时客户端的内建命令是本端行为，命令本身根本不会作为聊天消息发出去。
> 所以 ping 这条指令从头到尾只有使用者本人看得见。

---

**可能被问到："大家都在同一台电脑上，为什么还有时延？"**

这是个好问题，答案分两层：

1. **回环不是"没有网络"**，它是一个虚拟网卡。数据要走完整的内核 TCP/IP 栈
   （AFD → TCP → IP 回环驱动 → TCP → AFD），去一趟、回一趟，共两次。
   再加上两次**线程唤醒**（服务端的连接线程阻塞在 `recv()` 上，数据到达后由
   内核唤醒、调度器把它跑起来），以及我们自己代码的切帧/CRC32/发包开销。

   实测同机回环 RTT ≈ **0.2 ~ 0.5 ms**，与上述各环节的量级之和吻合。

2. **用微秒而不是毫秒显示**，否则看不到差别。本机真实 RTT 不足 1 ms，
   整数毫秒会恒显示 `0 ms`（看起来像"没测出来"）。
   程序用 `QueryPerformanceCounter` 硬件计时器，分辨率约 1 µs。

   参考量级：同机回环 0.2~0.5 ms，局域网 1~10 ms，跨城公网 30~100 ms。

### 环节 5：丢包检测（核心亮点，约 2 分钟）

**演示点**：实验要求第 7 条 —— 观察数据包丢失。

#### 5.1 正常网络下：观测不到丢包

先不加丢包，在任一客户端输入：

```
/test 100
```

> `/test` 的条数写成 `/test 100`、`/test [100]`、`/test[100]` 都可以，缺省是 20 条。

预期输出：

```
================= 丢包测试结果 =================
  发送测试报文数   : 100
  收到 ACK 数      : 100
  丢失报文数       : 0
  应用层丢包率     : 0.00 %
==================================================
```

**讲解词**：
> 这是**真实的观测结果**：TCP 通过重传和确认保证传输层不丢包，
> 所以正常网络下应用层观察到的丢包率是 0.00%。
> 这是符合预期的，不是没做检测——下面注入丢包就能看到检测确实在起作用。

**可能被问到："丢包率 0 是不是因为程序没测？"**

不是。丢包率 0 是**正确的观测值**，而不是"没测出来"。理由：

- 丢包的**检测机制与丢包的产生是分离的**：接收方只比对序号连续性，
  与"丢包是谁造成的"无关；
- 下面 5.2 人为注入 30% 丢包后，同一套代码立刻报出 38% —— 证明探测器是活的；
- 传输层丢包（TCP 重传后仍失败）确实为 0，因为 TCP 的可靠传输机制
  本身就**不允许**应用层看到丢包。实验要求"观察数据包丢失"，
  观察到的正是这一事实：**在可靠传输协议之上，应用层测不到丢包**；
  要在应用层制造并观测丢包，只能人为注入。

#### 5.2 注入丢包：检测立刻生效

**重启服务器并加 `--drop 30`**：

```bat
build\chat_server.exe -p 8888 --drop 30
```

客户端重新连上后执行：

```
/test 100
```

预期输出（**逐条告警 + 统计**）：

```
> [2026-11-04 14:26:25.712] 开始发送 100 条测试报文...
  ** 丢包告警: 服务端报文序号从 10 跳到 14, 中间丢失 3 帧 **
  ** 丢包告警: 服务端报文序号从 20 跳到 22, 中间丢失 1 帧 **
  ** 丢包告警: 服务端报文序号从 22 跳到 25, 中间丢失 2 帧 **
  ** 丢包告警: 服务端报文序号从 26 跳到 29, 中间丢失 2 帧 **
  ...
  ** 丢包告警: 服务端报文序号从 77 跳到 83, 中间丢失 5 帧 **

================= 丢包测试结果 =================
  发送测试报文数   : 100
  收到 ACK 数      : 62
  丢失报文数       : 38
  应用层丢包率     : 38.00 %
==================================================
```

**讲解词**：
> 每一帧报文带一个单调递增的序号。接收方发现序号从 10 直接跳到 14，
> 就知道中间 11、12、13 三帧丢了——**不需要超时重传去猜，序号一断就知道**。
>
> 关键设计：丢掉的帧**照样占用一个序号**。如果不占，序列看起来还是连续的，
> 接收方就完全发现不了丢失。这是调试中踩过的坑。

#### 5.3 两种独立方法交叉验证（最有说服力的一步）

紧接着执行：

```
/stat
```

预期输出：

```
================= 本端统计 =================
  已发送报文数     : 104
  收到的最大序号   : 106
  发现的序号缺口数 : 25
  丢失报文总数     : 38
=============================================
```

**讲解词**：
> 这里的 38 和上面 `/test` 算出的 38 是**两种完全独立的统计方法**得出的同一个数字：
>
> | 方法 | 原理 | 结果 |
> |---|---|---|
> | ACK 计数法 | 发出 100 条，实收 62 个 ACK | 38 |
> | 序号缺口法 | 由接收序号的最大空洞推算 | 38 |
>
> 两种方法独立却完全吻合，说明检测机制是准确的，不是碰巧。
> 注入 30% 而实测 38%，是因为人工丢包基于伪随机数逐帧判定，样本量 100 时的统计波动。

### 环节 6：反向丢包检测（约 1 分钟）

**演示点**：丢包检测是**双向**的，不只是客户端能发现服务端丢的。

**服务端不加 `--drop`**，客户端自己丢：

```bat
build\chat_client.exe -h 127.0.0.1 -p 8888 -n Dave --drop 30
```

**服务端窗口**预期输出：

```
[2026-11-04 14:26:16.419] 检测到用户 Dave(1) 丢失 1 个报文 (期望序号 3, 实际 4)
```

**Dave 客户端窗口**预期输出：

```
[2026-11-04 14:26:16.419] [可靠性] 服务端检测到你有 1 个报文丢失
```

**讲解词**：
> 反方向由服务端检测。服务端给每个客户端的报文编序号，客户端漏收时服务端能发现，
> 并通过 `LOSS_REPORT` 报文主动通知客户端："你有 N 个报文丢了"。
> 所以是**双向闭环**：谁丢了、被谁发现、都被告知。

### 环节 7：退出与收尾（约 15 秒）

在任一客户端输入：

```
/quit
```

其他客户端窗口预期出现：

```
[2026-11-04 14:25:32.492] [系统] pc1 离开了聊天室
[2026-11-04 14:25:32.492] [在线用户] pc2|pc3
```

**讲解词**：
> 客户端主动发 LOGOUT，服务器广播下线通知并同步更新在线列表。

## 三、备用：跑自动化测试

若评委要求"证明测试是自动化的"：

```bash
bash test/run_all.sh
```

实测输出：

```
# 测试 1/4: 编译
```

## 四、演示常见问题

| 现象 | 原因与处理 |
|------|-----------|
| `build.bat` 报 `g++ not found in PATH` | 未装 MinGW 或未加 PATH。安装后**重开**命令行窗口 |
| 客户端报「连接服务器失败」 | 服务器窗口未启动，或端口被占。换端口：两端都用 `-p 9000` |
| 客户端窗口中文乱码 | 用了旧版 cmd。程序已自动切 UTF-8 代码页，若仍乱码请改用 Windows Terminal |
| 时间戳 `[` 前面偶尔冒出一个乱码方块 | 旧版本的缺陷：主线程与接收线程并发写 stdout，两条输出在控制台行内交错，落到汉字的右半格就被渲染成替换字符。已用全局输出锁修复（见实验报告 §6 第 13 条）。**请用 `build.bat` 重新编译后再演示**，确认 `build\chat_client.exe` 的时间戳是新的 |
| 服务端首行显示 `监听 r:8888` 而不是 `监听 0.0.0.0:8888` | 同上，旧版本把 `std::string` 当 `%s` 传给了 `printf`，读出的是对象内存里的指针字节。已修复 |
| `/test [20]` 只发出 1 条报文 | 旧版本用 `atoi` 解析条数，`atoi("[20]")` 遇到 `[` 返回 0。已改为手写数字扫描，`/test 100`、`/test [100]`、`/test[100]` 都正确。请用 `build.bat` 重新编译 |
| `/who` 一直无输出 | 服务端未启动或连接已断。检查服务器窗口是否报错 |
| `/ping` 显示 `RTT = 0 us` | 用了旧版二进制。旧版用 `GetSystemTimeAsFileTime` 计时，其刷新粒度是系统时钟节拍（约 15.6 ms），毫秒与微秒差值都会是 0。请用 `build.bat` 重新编译 |
| 端口 8888 被占 | 换一个端口，两端同步改：`-p 9000` |
| `build.bat` 报 `cannot open output file ... Permission denied` | 演示中的服务器/客户端还占着 exe 文件。`build.bat` 已做换名替换处理（编译到 `.new.exe` 再改名），正常不会触发；若仍报错说明跑的是旧版 `build.bat`，请重新复制该文件 |
